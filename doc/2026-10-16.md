## 주제

오늘 저장소에는 2026-10-16에 추가된 새 학습 코드가 없었다. 따라서 가장 최근 학습 코드인 `day30`의 RAG 검색 흐름을 다시 정리했다.

1. PDF 문서 로딩과 텍스트 청킹
2. 임베딩과 FAISS 벡터 검색
3. Gradio 대화 기록을 포함한 RAG 체인
4. BM25 키워드 검색과 벡터 검색의 차이
5. `EnsembleRetriever`를 이용한 하이브리드 검색

## 중요한 내용

- RAG는 질문과 관련된 문서를 먼저 찾고, 찾은 내용을 LLM에 참고 자료로 넣어 답변하게 하는 방식이다.
- `PyPDFLoader`는 PDF를 `Document` 목록으로 읽고, text splitter는 긴 문서를 검색하기 좋은 작은 청크로 나눈다. 청크 사이에 겹치는 부분을 두면 경계에서 문맥이 끊기는 일을 줄일 수 있다.
- 임베딩은 글을 숫자 벡터로 바꾸는 과정이다. FAISS는 벡터 사이의 거리를 이용해 질문과 가까운 청크를 찾는다.
- BM25는 단어가 얼마나 겹치는지를 중심으로 검색한다. 벡터 검색은 표현이 달라도 의미가 비슷한 내용을 찾는 데 유리하다. 둘을 함께 쓰면 한쪽의 약점을 보완할 수 있다.
- `EnsembleRetriever`의 `weights=[0.5, 0.5]`는 BM25와 벡터 검색 결과의 결합에서 두 검색기의 가중치를 같게 주는 설정이다.
- `MessagesPlaceholder(variable_name="chat_history")`는 이전 대화 메시지를 프롬프트에 넣을 위치다. 대화 기록을 넣는다고 해서 모델의 기억이 영구적으로 저장되는 것은 아니다.
- `similarity_score_threshold`의 점수 의미와 범위는 사용하는 벡터 저장소와 거리 설정을 확인해야 한다. 숫자 `0.7`을 모든 검색기에서 같은 뜻이라고 단정하면 안 된다.

## 반드시 기억할 점

- 검색기(retriever)는 관련 `Document`를 찾고, LLM은 검색 결과와 질문을 바탕으로 답변을 만든다.
- `Document`는 본문인 `page_content`와 부가 정보인 `metadata`를 가진다.
- 검색 결과가 없거나 관련성이 낮을 때 어떻게 답할지 프롬프트에 적으면 환각을 줄이는 데 도움이 되지만, 문장 하나만으로 항상 정확한 거절이 보장되지는 않는다.
- `FAISS.load_local(..., allow_dangerous_deserialization=True)`는 신뢰할 수 있는 저장 파일에만 사용해야 한다.
- 외부 PDF, 임베딩 모델, FAISS DB, API 키, 패키지 버전이 필요한 코드는 정적 검토와 실제 실행 검증을 구분해야 한다.

## 코드 흐름과 shape 설명

1. PDF 로더가 페이지를 `Document` 객체 목록으로 읽는다.
2. text splitter가 각 문서를 여러 문자열 청크로 나눈다.
3. 임베딩 모델이 각 청크와 질문을 같은 길이의 숫자 벡터로 바꾼다.
4. FAISS가 벡터를 저장하고 질문과 가까운 벡터를 검색한다.
5. retriever가 검색한 `Document` 리스트를 체인에 전달한다.
6. 프롬프트는 질문, 검색 문서, 필요하면 `chat_history`를 함께 구성한다.
7. LLM이 그 입력을 받아 답변을 만들고 Gradio가 화면에 보여 준다.

문서 청크는 문자열 목록이고, 임베딩은 보통 `(문서 수, 임베딩 차원)`처럼 생각할 수 있는 벡터 모음이다. 실제 코드의 정확한 문서 수와 임베딩 차원은 실행 환경과 모델에 따라 달라질 수 있으므로, 주석에 적힌 과거 숫자를 이번 실행 결과로 사용하지 않는다. 검색 결과는 `Document` 객체들의 리스트다.

## 쉬운 예시

도서관에서 “비 오는 날 우산은 어떻게 고르나요?”라고 물었다고 하자. BM25 사서는 ‘비’, ‘우산’이라는 단어가 많이 나오는 책을 찾는다. 벡터 사서는 ‘우천용 방수 도구 선택’처럼 단어는 달라도 뜻이 가까운 글을 찾는다. 두 사서가 찾은 내용을 선생님(LLM)에게 보여 주면, 선생님은 그 자료를 참고해 답한다.
