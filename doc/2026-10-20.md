## 주제

오늘은 LangGraph 그래프에 외부 검색 도구를 연결하는 tool calling 흐름을 학습했다.

1. `TavilySearch`와 DuckDuckGo 검색 도구를 만들기
2. `llm.bind_tools(tools=tools)`로 모델이 사용할 수 있는 도구를 등록하기
3. `ToolNode(tools)`로 실제 도구 실행 노드 만들기
4. `tools_condition`으로 모델이 도구를 호출했는지에 따라 분기하기
5. `chatbot → tools → chatbot` 반복 흐름으로 검색 결과를 모델에게 다시 전달하기
6. LangGraph 그래프를 Mermaid PNG로 그려 파일로 저장하기

## 중요한 내용

- tool calling은 모델이 직접 웹을 읽는다는 뜻이 아니다. 모델이 “이 질문에는 검색 도구가 필요하다”고 판단하고, 도구 호출 정보를 만들면 `ToolNode`가 실제 검색 함수를 실행한다.
- `tools`는 모델에 등록할 도구 목록이다. `TavilySearch` 하나를 넣을 수도 있고, `lg06_02_ddg.py`처럼 Tavily와 DuckDuckGo를 함께 넣을 수도 있다.
- `llm.bind_tools(tools=tools)`는 도구를 사용할 수 있도록 설정한 새 모델 객체를 반환한다. 따라서 반환값인 `llm_with_tools`를 실제 `invoke()`에 사용해야 한다. 코드의 첫 번째 `llm.bind_tools(...)` 호출은 반환값을 저장하지 않아 실질적으로 사용되지 않는다.
- `ToolNode(tools)`는 모델의 tool call을 받아 해당 도구를 실행하고 결과를 메시지로 상태에 넣는 LangGraph 노드다.
- `tools_condition`은 보통 chatbot의 마지막 메시지에 도구 호출이 있으면 `tools`로, 없으면 `END`로 보내는 조건부 분기 함수다.
- `tools`에서 다시 `chatbot`으로 연결하면 검색 결과를 모델에게 보여 주고, 모델이 최종 답변을 만들 수 있다. 모델이 추가 도구를 요청하면 이 흐름이 더 반복될 수 있다.
- `State`의 `messages`는 사용자 질문, AI의 tool call 메시지, 도구 결과 메시지, 최종 AI 답변을 순서대로 담는 공용 기록이다. `add_messages`가 이 기록을 병합한다.
- `TavilySearch`와 DuckDuckGo는 외부 네트워크와 패키지 설치, 그리고 필요한 인증 설정에 의존한다. 코드에 있는 query의 주식 가격이나 모델 답변은 실제 실행 결과를 확인하기 전에는 사실로 기록하면 안 된다.
- `lg07_ToolNode_graph.py`의 PNG 저장은 `./_save/image/` 디렉터리가 이미 있어야 한다. 코드에는 디렉터리를 만드는 부분이 없으므로 디렉터리가 없으면 파일 저장 단계에서 실패할 수 있다.

## 코드 흐름과 shape 설명

1. 네 파일 모두 환경변수에서 모델 API 키·base URL·Tavily 키를 읽고 `ChatOpenAI`를 만든다. 실제 비밀 값은 문서에 기록하지 않는다.
2. 검색 도구를 만든다.
   - `lg05_ToolNode.py`, `lg07_ToolNode_graph.py`: `TavilySearch(max_results=3)`
   - `lg06_01_ddg.py`: `DuckDuckGoSearchRun(max_results=5)`
   - `lg06_02_ddg.py`: 두 검색 도구를 모두 `tools` 리스트에 넣음
3. 모델에 도구 목록을 바인딩하고 `StateGraph(State)`를 만든다.
4. `chatbot(state)`는 `state["messages"]`를 모델에 전달하고, 모델이 만든 메시지 하나를 `{"messages": [...]}` 형태로 반환한다.
5. `START → chatbot`으로 시작한다. chatbot이 도구 호출을 만들면 `tools_condition`이 `tools`로 보낸다.
6. `ToolNode`가 검색을 실행하고 결과를 상태의 `messages`에 추가한다. `tools → chatbot` 엣지가 있으므로 모델이 검색 결과를 읽는다.
7. 모델이 더 이상 도구를 호출하지 않으면 `tools_condition`이 `END`로 보내 그래프가 끝난다.
8. 최종 결과는 `response["messages"][-1].content`로 출력한다. 마지막 메시지가 항상 일반 텍스트라는 보장은 실행 결과와 모델 동작을 확인해야 하므로, 실제 프로그램에서는 메시지 타입과 오류도 점검하는 편이 안전하다.
9. `lg07`은 추가로 `graph.get_graph().draw_mermaid_png()`의 바이트 데이터를 얻고, 바이너리 쓰기 모드 `wb`로 PNG 파일에 저장한다. 배열 shape를 다루는 코드는 아니며, 여기서 중요한 형태는 “PNG 바이트 데이터 → 파일”이다.

## 쉬운 예시

도서관에 질문하러 가는 흐름으로 생각하자.

1. `chatbot`은 질문을 읽고 “도서관 검색이 필요해”라고 결정한다.
2. `tools_condition`은 검색이 필요하므로 검색 담당자인 `tools`에게 보낸다.
3. `ToolNode`는 실제로 책을 찾아 결과를 가져온다.
4. 결과가 다시 `chatbot`에게 돌아가면 chatbot은 검색 결과를 이용해 사람에게 답한다.
5. 검색이 더 필요 없으면 `END`에서 멈춘다.

도구를 모델에 알려 주는 것과 도구를 실제로 실행하는 것은 다르다. `bind_tools`는 사용할 수 있는 도구 목록을 알려 주는 단계이고, `ToolNode`는 선택된 도구를 실행하는 단계다.

## 반드시 기억할 점

- `bind_tools()`의 반환 객체를 실제 호출에 사용해야 한다.
- 모델이 tool call을 만들었다고 검색이 자동 실행되는 것은 아니다. 그래프에 `ToolNode`와 조건부 엣지를 연결해야 한다.
- `ToolNode → chatbot` 엣지가 있어야 도구 결과를 모델이 읽고 최종 답변을 만들 수 있다.
- `messages`는 단순히 질문과 답만 담는 리스트가 아니라 tool call과 tool result까지 포함할 수 있다.
- 외부 검색 결과와 주가처럼 변하는 정보는 코드의 주석이나 예상 출력이 아니라 실제 실행 결과로만 확인해야 한다.
- 환경변수 이름만 코드에 있어도 키가 실제로 유효하다는 뜻은 아니다. 키를 출력하거나 문서에 복사하지 않는다.
- PNG 저장 전에 대상 디렉터리가 존재하는지 확인해야 한다.
